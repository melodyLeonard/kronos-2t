# Engineering iterations

Design notes behind the current engine, in the order the pieces were built. Each item names the
code that implements it and the quantity it changed. README.md covers building and running;
BENCHMARKS.md holds the measurements.

1. Iteration 1 — Multiplication-free Four-Russians NEON LUT-GEMV and Cartesian product-key routing (`src/kernels/lut_gemv.rs`, `src/kernels/simd_lut.rs`, `src/kernels/router.rs`, `src/kernels/synthesis.rs`):
   - Precomputes $3^4 = 81$ (padded to 16-entry nibble tables) linear combinations of 4 input activations so ternary inner products $\sum_j w_{ij} x_j$ with $w_{ij} \in \{-1, 0, +1\}$ reduce to single-cycle ARM NEON `vqtbl1q_s8` register lookups with zero multipliers.
   - Multi-rank Kronecker codebook synthesis (`vqtbl4q_u8`) reconstructs sub-bit expert tiles inside SIMD registers without L1 spill.
   - Product-key routing decomposes $M$ experts into $C_1 \times C_2$ sub-keys ($\sqrt{M} + \sqrt{M}$ dot products), cutting routing complexity from $O(M)$ to $O(\sqrt{M})$.
   - **Limitation.** Ternary kernels need ternary weights, and pretrained Llama/Qwen2 checkpoints are not ternary. No speed or quality figure for this path is recorded in the repo. Real checkpoints need post-training quantization at 3-6 bits.

2. Iteration 2 — Page-aligned `.k2t` container, zero-copy `mmap` pager, and $O(1)$ State-Space Dual recurrence (`src/storage/k2t_format.rs`, `src/storage/mmap_pager.rs`, `src/kernels/ssd.rs`):
   - Aligns weight stripes to 4 KB / 16 KB virtual-memory pages mapped directly via POSIX `mmap` + `POSIX_MADV_WILLNEED` lookahead prefetching (`src/storage/prefetch.rs` rank-$r$ subspace residual projection $P_l x_t$).
   - Replaces $O(L)$ growing attention state in recurrent blocks with constant-memory fast-weight recurrence $S_t^{(h)} = \gamma_t^{(h)} S_{t-1}^{(h)} + v_t^{(h)} (k_t^{(h)})^T$, $y_t^{(h)} = S_t^{(h)} q_t^{(h)}$, using a 1-token causal induction shift on odd heads for bigram associative recall.
   - **Limitation.** The recurrence removes state growth only in recurrent blocks; transformer KV still grows with context (2,304 MiB at 32k positions in FP32 on SmolLM2-135M). Layout and paging do not address the error of low-bit weights on pretrained models (no figure recorded).

3. Iteration 3 — Block-64 randomized Walsh-Hadamard incoherence, Ledoit-Wolf Cholesky GPTQ, and $D_4$ lattice activation LUTs (`src/kernels/hadamard.rs`, `src/kernels/accel.rs`, `src/model/real_llm.rs`):
   - Heavy-tailed LLM weight and activation outliers destroy uniform low-bit grids. Applying the orthogonal signed Hadamard transform $Q_b = \frac{1}{8} H_{64} D_b$ ($D_b \in \{\pm 1\}^{64}$ Rademacher signs, $Q_b^T Q_b = I_{64}$) preserves exact inner products $\langle Q_b w_b, Q_b x_b \rangle = \langle w_b, x_b \rangle$ while bounding worst-case channel magnitude to $O(\sqrt{\log d / d})$ sub-Gaussian concentration.
   - Layer-wise GPTQ solves $\min_{\hat{W}} \| W X - \hat{W} X \|_F^2 = \mathrm{tr}((W - \hat{W}) H (W - \hat{W})^T)$ using damped Hessian $H = \frac{2}{N} X X^T + \lambda I$ and triangular inverse $H^{-1} = L L^T$ (via Cholesky factorization), propagating column quantization error $\delta_j = (w_j - \hat{w}_j) / [H^{-1}]_{jj}$ across remaining columns $w_{j:} \leftarrow w_{j:} - \delta_j [H^{-1}]_{j, j:}$.
   - Bipolar bit-plane decomposition $q = 2u - (2^B - 1) = \sum_{p=0}^{B-1} 2^p s_p$ ($s_p \in \{\pm 1\}$) executes low planes on `aarch64` `sdot` and higher planes (`p55454`, `b6`) via register LUTs; 4D checkerboard $D_4$ lattice rounding ($\sum_{i=1}^4 z_i \equiv 0 \pmod 2$) improves sphere-packing gain on activations.
   - **Limitation.** At 1.7B the 4-bit tier only ties llama.cpp (KL 0.050 vs 0.048 for IQ4_XS, 867 vs 895 MiB) and with generic calibration at 135M it falls behind (KL 0.085/0.101 vs 0.080/0.084 on WikiText/C4). Execution is CPU-only: 1.7B Bipolar-4 decodes 57 tok/s on one core and prefills 76 tok/s against 183 for llama.cpp. Batched GEMM is already at 85% of `sdot` peak and an `i8mm` (`SMMLA`) variant measured the same, so CPU prefill has no headroom. Uniform planes cost 4.25 bits against 4.13 for a Lloyd-Max codebook.

4. Iteration 4 — Spherical Lloyd-Max `NF3`/`NF4`/`NF5` codebooks, Hadamard `Q8`/`Q4` KV cache, and Core ML Neural Engine prefill (`src/model/real_llm.rs`, `src/backend/coreml.rs`):
   - Under Hadamard rotation, group-normalized coordinates follow a spherical Gaussian distribution $w \sim \mathcal{N}(0, \sigma^2)$. Non-uniform Lloyd-Max centroids $c_k = \mathbb{E}[w \mid w \in [t_k, t_{k+1})]$ minimize $\mathbb{E}[(w - c_{Q(w)})^2]$ for 8, 16, and 32 levels (`NF3`, `NF4`, `NF5`) with 128-element group scales (`4.125 bpw` for `nf4g128`).
   - Rotating keys and values by `FWHT-64` before `INT8` (`Q8`) or `INT4` (`Q4`) quantization cuts KV memory 4x–8x; sliding-window + attention-sink eviction (`sink + sliding`) bounds KV memory strictly at $O(W_{\text{sink}} + W_{\text{slide}})$ regardless of sequence length.
   - **Limitation.** `nf4g128` on SmolLM2-1.7B (842 MB) has KL 0.066 and PPL 13.52 against 12.81 for FP. The 14B on CPU needs 8.17 GiB of weights and 10.16 GiB RSS at 32k, decodes 21.5 tok/s and prefills 57.0 tok/s. Q4 KV halves KV memory (14B: 3.38 to 1.69 GiB at 32k) at about 0.03 nat KL and 3 points of top-1 on the 135M. The Neural Engine covers prefill only (about 340 ms to first token against 650-850 ms for 290 tokens); decode stays on the CPU.

5. Iteration 5 — Zero-copy `Metal.framework` GPU `simdgroup_matrix` engine and lossless heterogeneous CPU-draft speculative decoding (`src/backend/metal_gpu.rs`, `src/runtime/chat.rs`):
   - Maps `.k2tb` weights into unified Apple Silicon RAM with `MTLStorageModeShared` (`0` copy bytes) and dequantizes `NF3`/`NF4`/`NF5`/`E8Q2` codebooks in threadgroup SRAM feeding `simdgroup_matrix` FP32 accumulators.
   - Runs a `0.5B` draft model on CPU P-cores while the `14B` target verifies $K+1$ tokens in a single batched Metal pass, accepting drafted token $x_i$ with probability $\min(1, p_{\text{target}}(x_i) / p_{\text{draft}}(x_i))$ so the output distribution equals the exact target distribution while doubling decode throughput (`48.5 tok/s` on `Qwen2.5-Coder-14B`).
   - **Limitation.** The 14B is dense, so every token reads all 8.17 GiB; Metal alone decodes 25.1 tok/s against 26.0 for llama.cpp Q4_K_M. The 48.5 tok/s relies on 74.1% draft acceptance and idle P-cores; on a loaded machine the 14B + draft runs were within noise of plain decoding, and free-form acceptance was 142/361. Quality is bounded by the 14B: the agent suite passed 3/10 and 2/10 tasks. A larger dense model does not fit 24 GB, so the remaining lever is sparse activation, which makes expert storage the constraint.

6. Iteration 6 — Physical `F_NOCACHE` NVMe SLRU expert streaming and `k2di` sub-millisecond device/voice runtime (`src/model/moe_800b.rs`, `src/runtime/device.rs`, `src/runtime/speech.rs`):
   - Streams 16 KB-aligned `.k2tm` MoE experts directly from NVMe Flash via `fcntl(fd, F_NOCACHE, 1)` + `pread` into a bounded probationary/protected SLRU DRAM pool, bypassing macOS unified buffer-cache double-buffering so OS page caches cannot evict active attention weights.
   - Indexes local macOS apps, projects, `.venv` toolchains, and documents into an FNV-1a word + 3-gram posting list (`device_index.k2di`) queried in `< 2 ms`.
   - **Limitation.** `bench_800b` uses synthetic weights and gives no quality figure. All-SSD reads give 0.78 tok/s (5.9 GB/s); Zipf routing with cache and prefetch gives 1.64 tok/s at a 47% hit rate, and real routing is flatter, so the hit rate will be lower. The 13-24 tok/s all-in-RAM bound does not fit 24 GB at 3 bits. NF3 experts keep 0.96 cosine to FP32 but scalar 2-bit VQ2 only 0.86, so expert bytes could not shrink further without a better 2-bit code.

7. Iteration 7 — Gosset $E_8$ 8-dimensional lattice 2-bit quantization (`e8q2g128`, `2.125 bpw`) with Cholesky-Wagner GPTQ and `Edge8G` / `Mobile5G` `20.91B` Sparse-MoE budgets (`src/kernels/hadamard.rs`, `src/model/sparse_moe.rs`, `src/model/memory_budget.rs`, `src/ffi/mobile_ffi.rs`):
   - Scalar 2-bit quantization (`VQ2`) collapses at `2.1 bpw` (`35 PPL` vs `12.8`). By Viazovska's theorem, the 8D Gosset lattice $E_8 = D_8 \cup (D_8 + \frac{1}{2}\mathbf{1}_8)$ (where $\sum_{i=1}^8 z_i \equiv 0 \pmod 2$) achieves optimal 8D sphere packing ($\Delta_8 = \pi^4 / 384$) and minimal normalized second moment $G(E_8) = \frac{929}{12960} \approx 0.07168$ vs $G(\mathbb{Z}) = \frac{1}{12} \approx 0.08333$.
   - `e8q2g128` packs 256 codebook vectors ($1$ zero + $240$ minimal-norm shell-1 roots $\|v\|^2 = 2$ + $15$ shell-2 axes) into `2 bytes` per 8 weights (`2.0 bpw` + FP16/128 scale = `2.125 bpw`), using Wagner shortest-parity rounding ($O(8)$) inside block-8 Cholesky GPTQ ($8 \times 8$ block error feedback $H_{B,B}^{-1}$).
   - Combined with `NF4` untied embeddings, `Q4` sliding-sink KV, and bounded SLRU/mmap expert paging, a `20.91B`-parameter Sparse-MoE (`3.6B` active, top-4 of 32 experts) runs inside `3.83 GiB <= 5.00 GiB` RSS on 8 GB Macs (`69.7 tok/s`) and `4.01 GiB <= 4.90 GiB` RSS under iOS `os_proc_available_memory` limits (`32.4 tok/s`, exported as `aarch64-apple-ios` `libkronos_2t.a`).
   - **Limitation.** The 20.91B budget model is reported for RSS and throughput only (3.832 GiB at 69.7 tok/s; 4.006 GiB at 32.4 tok/s). No PPL, KL or eval pass rate is recorded for it, and E8 is compared with scalar VQ2 only qualitatively at 135M. Whether such small, aggressively quantized models make correct decisions was not measured, and no trained coding MoE was compiled, which leads to output verification and a real MoE.

8. Iteration 8 — `Kronos-Jev` single-forward-pass calibrated decision primitives and monotonic rubric verification (`src/runtime/jev.rs`, `src/runtime/agent.rs`):
   - Generative multi-token judges spend hundreds of decode tokens (`~497 ms` on `0.5B`, seconds on `14B`) with uncalibrated verbal confidence. `Kronos-Jev` scores anchor token sets $\mathcal{A}_k$ in one forward pass (`13.72 ms` neural with cached prefix KV snapshot/restore, `0.016 ms` structural) and fuses structural log-odds $l_0$ with neural Bayes-factor log-odds via $l_{\text{post}} = l_0 + \alpha \log \frac{P(Y)}{P(N)}$, where $\alpha = w_{\text{neural}} \cdot \mathrm{clamp}((m - 0.05)/0.55, 0, 1)^2$ shrinks automatically to $0$ when anchor probability mass $m$ is diffuse or when deterministic compiler/syntax/DOM/file oracles give exact ground truth.
   - Pre-turn KV-aware schema pruning cuts cold tool-schema tokens by `55.4%` while preserving `0 ms` hot KV prefix reuse, and monotonic checkpointing rolls back regressions if post-edit verification drops below the verified high-water mark.
   - **Limitation.** Jev reaches 94.4% accuracy (Brier 0.0307, ECE 0.0672) but only judges output; it does not raise generation quality or lower its cost. The agent suite on the 14B passed 3/10 and 2/10 tasks, and in the later run 13 of 20 follow-up turns ended without a final reply. The largest model that ran was the dense 14B, and a 30B MoE needed a 48 min CPU compile.

9. Iteration 9 — Metal GPTQ compiler, decode-path kernels, and conversation-aware serving (`src/backend/metal_compile.rs`, `src/backend/metal_gpu.rs`, `src/runtime/chat.rs`, `src/bin/kronos_server.rs`):
   - The MoE expert compile runs on the GPU: a Hadamard rotation kernel, the GPTQ scale search (11 candidate scales plus a least-squares refit, 8 rows per SIMD group) and the column error back-propagation $w_{j:} \leftarrow w_{j:} - \delta_j [H^{-1}]_{j, j:}$, plus the calibration forwards that feed the next layer's Hessian. Compiled with fast math and FP contraction off, the quantized indices and scales are bit-identical to the CPU compiler; experts are batched 8 per dispatch. Qwen3-Coder-30B-A3B compiles in 12.3 min against 48 min on CPU.
   - Per-token decode was profiled on the GPU clock per kernel class (`KRONOS_DECODE_PROF=1`). The router moved from one threadgroup per layer to one SIMD group per expert with coalesced loads plus a parallel softmax/top-k (10.5 ms to 1.0 ms per token). Attention splits the key sequence over up to 64 threadgroups with a log-sum-exp merge kernel, and the Q8 head-dim-128 loop scores 32 keys per step with one lane per key. Single-token gemvs split their columns across threadgroups with a reduce kernel, and the MoE gemv maps one row per lane so the 3-bit unpack branches are SIMD-uniform. 30B nf3 decode: 31.8 to 60.1 tok/s at short context, 19.3 to 40.9 tok/s at 6.6k tokens. For multi-token steps (prefill, speculative verify) a grouping kernel buckets the routed slots by expert into tiles of 16 and an indirect dispatch runs one threadgroup per (stripe pair, tile), so an expert's weights are unpacked once per tile; prefill went from 179 to 328 tok/s and code edits with prompt-lookup speculation from 47.6 to 65.5 tok/s. Verify batches stay bounded by expert diversity: 6 tokens touch about 40 distinct experts, so a batch costs about 5 single steps.
   - Serving: the model is handed out in arrival order with browser requests ahead of API and background agent steps; the KV cache of a conversation being left is snapshotted (Metal included) and restored on return, so switching conversations costs a copy instead of a prefill; hot experts chosen from a routing histogram are the only part of the shard wired in RAM (`--moe-hot`, `--moe-wire-gib`).
   - **Limitation.** The 30B `nf3nf4g128` needs a 10.6 GiB expert shard plus 0.8 GiB core on a 24 GB Mac; wiring 9 GiB covers 97% of routed tokens, and the other 3% page from disk (no latency recorded). Decode falls from 60.1 to 40.9 tok/s at 6.6k tokens, prefill is 328 tok/s, and speculative verify is bounded by expert diversity (about 5 single steps per batch). On the agent suite the 30B passes 8/10 tasks with nf4 experts and 6/10 with nf3 (the long-context task and two follow-up tasks fail), so the 3-bit expert tier costs quality that is not yet recovered. Dense-model compiles (about 12 min at 1.7B) and bit-plane tiers remain CPU-only.

10. Iteration 10 — grouped-query decode attention on simdgroup matrices (`src/backend/metal_gpu.rs`)
   - Decode attention at long context was instruction-bound and read each KV head once per query head (8 times for the 30B). The new kernel runs one threadgroup per (KV head, token, key split): each SIMD group takes 8 keys per step, expands K and V from Q8 to half in threadgroup memory once for the whole group, forms $S^\mathrm{T} = K Q^\mathrm{T}$ for the 8 query heads with `simdgroup_multiply_accumulate` (float accumulation), runs the online softmax per head in registers and accumulates $O \mathrel{+}= P V$ on 16 matrix tiles. A running-max change rescales $O$ by a diagonal matrix product. Partials keep the layout of the per-head kernel, so the split merge is unchanged. 30B nf3 decode at 6.6k tokens: 38.3 to 45.1 tok/s; short context 59.5 to 60.3 tok/s. The key split size (16 to 128 keys per threadgroup) made no difference above noise.
   - Null result: fusing the small single-token kernels (router top-k with the post-attention norm, split-K reduce with SwiGLU+FWHT, down reduce with the combine and the next norm, attention epilogue with the FWHT) removed 6 of 18 dispatches per layer and changed decode by 0.1 tok/s (59.1 to 59.2). The per-kernel times the profiler attributed to those kernels were the cost of its own command-buffer cuts; the fusion was reverted.
   - **Limitation.** Attention is still about 5.5 ms per token at 6.6k on top of the 16.6 ms context-independent floor, and the per-token weight traffic (3-bit experts, nf4 attention) sets that floor. Expert quality (6/10 agent tasks on nf3 against 8/10 on nf4) and the 4 KB per position Q8 KV cache remain the open costs.
